# UI / UX・ソフトキーボード・学園祭運用

## 1. UXの主目的

小学生が「ひらがなを入力 → 自動で動く → 失敗理由を知る → 短くする / 速くする」を短いサイクルで楽しめるようにする。操作を簡単にしても、Scratch型の命令ブロックUIにはしない。

## 2. 画面一覧（案）

| 画面 | 主な内容 |
| --- | --- |
| ホーム / ステージ選択 | ステージカード、難易度、クリア済み表示、ランキング導線 |
| プレイ / 編集 | 自由入力エディタ、実行、Canvas、必要ならソフトキーボード |
| 失敗結果 | 衝突理由、直し方のヒント、編集に戻る |
| クリア結果 | ゲーム内タイム、文字数、3つの得点、自己ベスト比較 |
| ランキング | 3タブ（タイム・文字数・総合）、ゲスト名 / 登録名、順位 |
| スタッフ操作 | 体験終了 / 初期化、端末の通信状況、動作確認 |

## 3. エディタ

- ブロック・パーツ選択式の入力UIは提供しない。
- ひらがなで自由なテキスト入力ができるtextarea等を採用する。
- 行番号または行ガターを表示し、エラー行を明示する。
- 有効判定は正式なParser/AST診断結果から取得する。辞書単語が含まれるだけで「正しい」と判断しない。
- 「なぜ動かないか」を短いひらがなで説明する。
- コードを編集してから実行する。ゲームの実行中にプレイヤーを手で操作しない。
- 失敗後は入力済みコードを保持して編集に戻れる。
- 使用可能な命令の説明は「説明ページ / ヒント」に置く。クリックで命令文字列を組み立てるブロック/パーツUIにはしない。

## 4. マウスで入力するソフトキーボード

### 採用の目的

物理キーボードの日本語入力に慣れていない児童でも、マウスのみでひらがなを入力できるようにする。

### 要件

- 五十音を基本に、濁点、半濁点、小書き文字、長音符、数字、空白、改行、削除を扱う。
- 表示/非表示を切り替えられる。
- エディタと同じ文字列 / カーソル位置 / 選択範囲に対して入力する。
- 選択範囲の置換と任意位置への挿入に対応する。
- Backspace、改行、カーソル移動、必要ならUndoに対応。
- マウス操作を前提に、誤クリックしにくいボタンサイズと余白にする。
- ソフトキーボードと物理キーボードを混在させてもデータが破損しない。
- ソフトキーボードのクリックでテキスト選択・フォーカスが失われないよう注意する。
- エディタとキーボードを同じ画面内に収めるが、ゲーム画面を極端に圧迫しない。
- 日本語IMEではcompositionstart / compositionend中の入力を不適切に削除しない。
- 画面のスクロール位置・エディタのガター表示ズレを検証する。

### 非対象

- 命令語（`かべとぶ`など）を完成済みの選択パーツとして並べること。
- Blockly/Scratch型のブロック組み立て方式。
- 文字サイズ変更機能。表示ズレと開発コストの増加を避け、固定の読みやすい基準文字サイズを採用する。

## 5. 成功・失敗フィードバック

- クリア時は得点を大きく表示。「はやさ」「もじのすくなさ」「そうごう」それぞれを明確にする。
- 1000点を超えたら「きじゅんをこえた！」などの達成演出を検討。
- 失敗時は「どの障害物で」「どんな動作が必要だったか」を説明する。
- 問題のある命令行をハイライトする。構文エラーはゲーム失敗とは区別する。
- ランキング保存失敗をゲームの失敗表示に混ぜず、再送できることを伝える。
- スタッフが声掛けしやすい短い文言を採用。

## 6. ランキング登録

- 名前入力欄は任意。空欄なら「ゲスト1」など連番をサーバーで割り当てる。
- 名前を入力した場合はその名前を表示。重複可。
- 入力名の長さ上限・制御文字拒否を設ける。
- 「ほんみょうはかかなくていいよ」等の簡単な案内を添える。
- ランキングは3種類を切り替えられる。自己ベストが異なる解法から成立することに対応。
- 他人のプログラム公開は今年の必須対象外。

## 7. 共用端末の運用

想定フロー:
1. スタッフがホーム / 体験開始状態にする。
2. 児童が自由入力またはソフトキーボードでプログラムを書く。
3. ゲームを繰り返し実行し、ランキングを必要に応じて登録。
4. 終了時は「つぎのひと」等のスタッフ用初期化で編集内容とローカルの本人情報を削除。
5. 次の体験者に引き継ぐ。

- 初期化はランキングのクラウド記録を削除しない。
- 意図せず管理ページにアクセスしただけで全ステージ解放されないようにする。
- 通信不調時もステージ実行を優先する。
- 事前に使用PCの解像度・ブラウザ・マウス設定・ネットワークを確認する。
- 運営用案内（操作方法、想定トラブル、リセット手順）を短いチェックリストにする。

## 8. 自宅での体験

- サイトを開くだけで初めから遊べる。
- QRによるランキング / 進捗移行は提供しない。
- 自宅でゼロから始めるコストが低いことを設計前提とする。
- 同じブラウザ内で最近の入力コードを保持する便利機能は任意。ただし別端末で同じプレイヤーと識別する機能は作らない。

## 9. アクセシビリティと表示

- 小学生が読めるひらがな中心の文言。
- エラーは赤だけで示さず、言葉やアイコンでも意味を伝える。
- ボタンのクリック領域とキー間余白を確保。
- 効果音を導入する場合は音量・ミュートを用意し、会場での運用を考慮。
- 個別の文字サイズ変更UIは今回対象外。
- 対応端末 / 最低画面幅を決めてからレイアウトテストを行う。

## 10. 検証観点

- 物理キーボードが苦手な人でもマウスのみで入力・修正・実行できる。
- ひらがなの小書き・濁音が意図どおり入力できる。
- コードを消さずに繰り返し試せる。
- 画面移動・モーダル閉じ・ステージ変更で表示が破綻しない。
- 次の体験者へ移る際、前の入力コードや名前が残らない。
- スコア1000点超えと、3ランキングの順位が直感的に理解できる。
