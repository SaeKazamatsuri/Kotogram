# ステージ設計・ギミック・自動検証

実装済みの第1段階の検証CLI（2026-10-18）: [ステージ検証CLIと基準解法](stage-validation-cli.md)。既存ステージの想定クリア・失敗解法、tick回帰スナップショット、文字数、既知の最良値、CIの実行方法を記載。自動解法探索と高速化可能な物理・命令は後続の作業。

## 1. 目標

ステージの価値は「クリアできるか」だけではない。初回体験者が意味を理解してクリアでき、慣れたプレイヤーがより短いプログラムやより速いプログラムを発見できることを重要視する。

自動検証はステージ追加・物理パラメータ調整・構文拡張による破壊的変更を検出するための必須基盤とする。

## 2. ステージに設定する情報

推奨フィールド:
- id、version、title、difficulty、learningObjectives。
- objects[]: 安定ID、type、位置、サイズ、初期状態・パラメータ。
- goal / clearConditions / failConditions。
- playerSpawn、scrollSpeed、physicsPreset、tickLimit。
- allowedVocabulary / allowedActions / languageFeatures。
- beginnerHint / failureHints / examplePrograms。
- rankingBaseline: T_ref、C_ref、P_ref、baselineVersion、探索範囲と由来。
- checks: 想定解法、想定失敗解法、達成可能なタイム範囲、使用可能ギミック。
- stageGroup / mode: 学園祭向け・自宅向け等の表示制御。

既存の `public/stages/*.json` と `public/stages/manifest.json` は移行対象。配列と数値の正当性をZod等で検証できる仕組みを検討する。

## 3. レベルデザインの原則

- 1ステージにつき主な学習目標を1〜2件に絞る。
- まず理解しやすい長い命令でクリアできる状態にする。
- 表記を省略したり条件を結合したりすると文字数が減る余地を用意。
- 速度変更やルート選択でタイムが短縮する余地も用意。
- 「まえとぶ」だけで通るステージがあってよい。ただし全ステージがそれだけで攻略できないよう障害物の組み合わせを工夫する。
- 短い命令が余計な対象に反応して失敗しうるステージを用意。
- 複合条件、しゃがみジャンプ、回数限定発火が活躍する場面を意図的に置く。
- 障害物の数、速度、間隔、開始位置で反応可能な猶予を設計する。
- 理解困難な「隠された正解」や偶然のフレームタイミングには依存しない。

## 4. 学習進行の案

| 段階 | 学習内容 | 例 |
| --- | --- | --- |
| 入門 | ひらがなの命令と実行 | とぶ / かべとぶ |
| 基礎1 | 条件に応じて反応 | かべ・あな |
| 基礎2 | 別種の行動の共存 | おばけしゃがむ |
| 基礎3 | 条件のOR結合 | かべとあなとぶ |
| 応用1 | 一般化 / 短縮 | まえとぶ |
| 応用2 | 回数制限 | かべ3かいとぶ |
| 応用3 | 速度と危険の両立 | はしる / あるく |
| 発展 | 複数条件、速度、回数の組合せ | 自由最適化 |

学園祭での体験時間、初級ステージ数、自宅向け追加コースの規模は参加者の観察から決める。

## 6. ギミック実装インターフェース案

ギミックは型IDと状態、衝突判定、検知、更新、描画メタ情報を持つ。各ギミックを個別のGameCanvas分岐で増やさず、共通APIへ集約する。

~~~ts
type StageObject = {
  id: string;
  type: string;
  x: number;
  y?: number;
  width?: number;
  height?: number;
  options?: Record<string, unknown>;
};

type MechanicsDefinition = {
  type: string;
  validate: (object: StageObject) => void;
};
~~~

実装例の型は固定したAPIではない。検知・物理・描画の結合度を低くするため、エンジン本体とは責務分割する。

## 7. 自動検証ランナー

CLIからheadlessでステージとプログラムを読み込み、同一エンジンでシミュレーションする。

~~~text
stage.json + program.txt + engine version
  -> JSON validation
  -> parse / semantic analysis
  -> deterministic simulation
  -> clear or fail + elapsedTicks + charCount
  -> score evaluation
  -> test report
~~~

必須検査:
1. スキーマ妥当性: IDの重複、範囲外座標、未定義のギミック、負の幅、矛盾するゴール。
2. 到達性: 想定した最低1つの解法でゴールできる。
3. 教育解法: 丁寧な構文で想定結果になる。
4. 短縮解法: 省略・複合条件によって文字数を改善できる。
5. 高速解法: 計測対象の時間を改善するケースが成立する。
6. 失敗解法: 想定ミスがきちんと失敗し、妥当なヒントが出る。
7. 同一性: 同じ入力を複数回実行しても同じ結果。
8. 回帰: エンジン変更で過去のテストケースが壊れない。
9. 安全性: ループ / tick / プログラム長の制限に到達しても終了する。

## 8. 自動探索（段階導入）

目的はレベルデザイン支援であり、全候補の数学的最適性証明を必須にしない。

P0: 手書きの基準解法・失敗解法の回帰実行。
P1: 命令語彙・許可構文・最大文字数を指定して短いプログラム候補を生成・探索。
P1: ベストタイム、最短文字数、最良タイム×文字数を別々に記録。
P2: 分岐限定・枝刈り・探索結果キャッシュ・制約の推論。
P2: 最適性を証明できた範囲と未探索範囲を明記。

探索には必ず最大候補数・最大実行tick・最大秒数・最大文字数を設ける。探索で新たな良解を発見しても公開中のランキング基準を自動的に変更しない。

## 9. レポート形式の案

~~~json
{
  "stageId": "stage-2",
  "validation": "pass",
  "engineVersion": "v-next",
  "programsChecked": 24,
  "beginnerSolution": { "clear": true },
  "shortSolution": { "clear": true },
  "fastSolution": { "clear": true },
  "bestKnown": {
    "elapsedTicks": null,
    "characters": null,
    "timeCharactersProduct": null
  },
  "warnings": []
}
~~~

数値は実測で埋める。計画段階では根拠のないスコアを使用しない。

## 10. 完了条件

- 全公開ステージに少なくとも1つの基準解法が紐付く。
- P0ステージの回帰テストがCIで通る。
- 複数速度・複合条件・しゃがみジャンプを含むステージを検証できる。
- 新ステージ追加がJSONと検証ケースの追加中心で完了する。
- ステージ制作者がクリアタイム・文字数・失敗理由を比較できる。
