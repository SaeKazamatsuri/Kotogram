# 採点・記録・ランキング仕様

## 1. 競技の対象

各ステージで競うのは3つ:
1. タイム: キャラクターが自動でスタートしてからゴールするまでのゲーム内時間。
2. 文字数: クリアに使ったプログラムの文字数。
3. 総合: タイムと文字数の両方を改善する成果。

プレイヤーの入力所要時間、クリック速度、描画FPS、ネットワーク応答時間は競技対象に含めない。

## 2. 基準スコア方式

ユーザーの希望により、小さい「コスト値」を1位の得点として表示せず、高得点ほど優秀なスコアとして表示する。

ステージ別に以下を保持する:
- T_ref: 公開時に確定した基準最短ゲーム内タイム（tick単位を推奨）。
- C_ref: 公開時に確定した基準最小文字数。
- P_ref: 公開時に確定した基準の最小「時間×文字数」。

重要: T_ref と C_ref は別々のプログラムから得られ、P_ref も独立したベスト解から得られうる。T_ref × C_ref を P_ref に代入してはならない。

計算式（T、Cは有効な正の数）:

~~~text
timeScore     = 1000 × T_ref / T
characterScore= 1000 × C_ref / C
overallScore  = 1000 × P_ref / (T × C)
~~~

- 表示用点数は必要に応じて整数に丸める。比較・順位の決定には丸め前の元記録を用いる。
- タイムランキングはT昇順、文字数ランキングはC昇順、総合ランキングはT×C昇順。スコアは高いほど良い。
- 最適解だと証明できないステージのT_ref等は「既知の最良解に基づく基準値」であり、理論下限だと断言しない。
- 基準値よりも優れた解法は1000点超えを許可する。表示点数に1000点の上限を設けない。
- ステージ公開中は基準値を固定して、ユーザーの過去得点が勝手に変化しないようにする。変更するときはランキングバージョンを切り替える。
- 文字数0でクリアできるステージの扱いは要決定。初期仕様では「有効命令1文字以上を必要とするステージ」をランキング対象とする。

## 3. タイムと文字数の詳細

### タイム

- 公式記録はゲーム内tick整数を正本として保存。
- タイム秒表示はtick / tickRateとし、表示時の丸めと順位の判定は分離。
- 実行ボタンを押してゲーム開始状態になった後、キャラクターが動く区間から計測。
- 失敗・タイムアウトにはクリアタイムを付与しない。
- 一時停止を導入する場合は停止中tickを進めない。
- 改変が結果へ影響する場合、engineVersion / stageVersionでランキングを分ける。

### 文字数

- ひらがな・数字など、ソースに実際に記述した有効な表示文字を数える。
- 改行・無意味な空白・インデントはカウントしない案（最終的なスペース規則は公開前に凍結）。
- 省略可能な助詞等を削ったことによる短縮は反映する。
- 同義語でも記述文字数は異なるため、同義語の短さが解法の工夫になりうる。
- Unicodeの表示文字単位で計測。濁点、合成文字、全角数字の扱いは同じ正規化処理を使用する。
- サーバー保存する場合は元のソース、正規化後の文字数、仕様バージョンを関連付ける。

## 4. ベスト記録は3種類独立

同じプレイヤー・同じステージの
- bestTime: 最小tickとそのプログラム。
- bestChars: 最小文字数とそのプログラム。
- bestOverall: 最小tick×文字数とそのプログラム。
をそれぞれ保持する。

最速と最短と総合最良が必ずしも同じ挑戦にはならない。記録の更新では、それぞれ別々に改善判定をする。

推奨される同点順序:
- タイム: tick昇順、次に文字数昇順。
- 文字数: 文字数昇順、次にtick昇順。
- 総合: tick×文字数昇順、次にtick昇順、次に文字数昇順。
- 完全同点は同順位とし、画面上の安定表示順だけ内部ID等で固定。タイムの表示丸めによって同点判定しない。

## 5. ゲスト番号・表示名

- 名前未入力時は「ゲスト1」「ゲスト2」…のようなサーバー発行の連番名を付ける。
- ユーザーが名前を入力した場合はその文字列を登録・表示する。内部の識別子は名前から独立させる。
- 名前の重複を許容。名前で同一人物判定をしない。
- 初回ランキング登録時にゲスト番号を発行する案（未クリア体験者に番号を割り当てない）。
- DO上のcounterを単一の連番発行元にするか、シーズン別にcounterを分けるか決める。
- 入力名には長さ・制御文字等の最低限の制限を設け、実名・個人情報を入力しない案内を表示する。
- 学園祭の共用端末では次利用者へ渡す前に現在の表示名とローカル記録を削除。
- 自宅で再スタートするためにQR、復帰コード、ログインは使わない。

## 6. ランキングのスコープ

キー: seasonId + stageId + rulesetVersion + rankingVersion

- ステージ別にタイム・文字数・総合の上位N件を取得できる。
- 本人の順位や自己ベスト表示は端末内のplayerIdが残る場合に限って提供可能。
- 同一ニックネームの別プレイヤーは統合しない。
- 同一端末の再挑戦では同じローカルplayerIdを使って自己ベストを更新する案。
- イベント共用端末は体験者が変わるたびにplayerIdを入れ替える。
- 他端末では基本的に別プレイヤーとして開始する。端末横断引き継ぎはスコープ外。
- 複数の期間ランキング（2026学園祭、公開後など）は将来設計で切り替えられる構造にする。

## 7. 保存モデルの候補

~~~ts
type RunRecord = {
  runId: string;
  playerId: string;
  nickname: string;
  seasonId: string;
  stageId: string;
  stageVersion: string;
  engineVersion: string;
  languageVersion: string;
  scoringVersion: string;
  elapsedTicks: number;
  charCount: number;
  source: string;
  createdAt: string;
};

type BestRecords = {
  timeRunId?: string;
  charsRunId?: string;
  overallRunId?: string;
};
~~~

これらは概念モデル。実DBの主キー・インデックス・保存量・シーズン情報は [システム構成](architecture-data.md) で調整する。

## 8. ランキング登録フロー

1. クリア画面で公式tickと文字数を確定する。
2. 名前を入力するか空欄を選ぶ。
3. APIへラン記録を送信。最低限の値検証と重複送信防止を行う。
4. 新規ゲストなら連番表示名を発行する。
5. そのステージの各ベスト記録を独立更新する。
6. ランキング取得・自己ベスト更新・1000点超えなどを表示する。
7. 通信失敗時はゲームクリアを取り消さず、ローカル記録を表示して再送できるようにする。

## 9. 軽量な不正対策の範囲

子ども向けの学園祭ゲームを想定し、サーバー側で全走行を再現する常時アンチチート等は今年版の必須対象にしない。名前長、プログラム最大長、tickや文字数の妥当範囲、送信件数の上限、重複送信排除を実装する程度とする。後で検証を追加できるよう、runId・source・versionを保存可能な形にする。

## 10. 受け入れ条件

- ステージ内で3つの順位が独立して更新される。
- 同一挑戦が別々のランキングで上位になれる。
- 1000点を超えた記録が上位として表示される。
- 単なる表示丸めが同点順位を生まない。
- ニックネーム未入力時に重複しないゲスト番号が発行される。
- ステージバージョンが異なる記録を混在表示しない。
- 保存失敗でゲームが止まらない。
