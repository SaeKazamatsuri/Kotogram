# ことグラム言語仕様 v1（設計案）

## 0. 状態とねらい

- 採用確定: ひらがな自由テキスト、非インデント構文、短縮表現、条件付き継続監視、回数制限、複合条件OR、ハイブリッド実行。
- 実装前に要試験: 複合ブロックの反復、無条件アクションの実行待機、ルール競合と速度変更の優先規則。
- 本文の入力例は仕様候補を含む。辞書に追加しただけで自動的に何でも解釈する仕様ではない。

学習者の目標は「長く丁寧に書いた文」から「意味を保った短い文」へ縮めること。命令パーツUIを提供しない。

## 1. 文字体系と正規化

- 許容する主な文字: ひらがな、長音記号、0〜9（半角 / 全角）、空白、改行。記号の取り扱いは構文仕様に応じて明示する。
- Unicodeは正規化し、合成済みの濁点・半濁点の入力も意図どおり扱う。
- 全角数字は半角数字に変換して意味解析する。
- 構文上、空白の有無と行頭インデントは原則無視。Tab自体の入力は無害化または除去し、ブロック構造には使用しない。
- 見かけ上同じ入力は同じASTになること。表示用ソースと実行用の正規化ソースは区別する。
- 文字数は、不要な空白・改行を除去した表示文字の数として計算する案。濁点・Unicode正規化とランキングの一貫性をテストし、最終規則を固定する。

## 2. 語彙辞書

### 動作語

| ID | 基本語 | 同義語の候補 | 意味 |
| --- | --- | --- | --- |
| jump | とぶ | じゃんぷ | ジャンプの開始 |
| crouch | しゃがむ | かがむ | しゃがむ状態 |
| walk | あるく | — | 基準速度の移動 |
| run | はしる | — | 速い移動 |
| wait | まつ | — | 決められた条件まで待機 |
| collect | とる | ひろう | アイテム取得（ギミック導入後） |

動作語の詳細な使用可能範囲はステージ設定で制限できる設計とする。P0で扱う動作集合は実装優先順位に従う。

### 条件語

| ID | 語彙例 | 意味 |
| --- | --- | --- |
| wall | かべ | 検知範囲内の壁 |
| hole | あな | 検知範囲内の穴 |
| enemy | おばけ / てき | 検知範囲内の敵 |
| ahead | まえ | 前方にある、対象種別を限定しない検知 |
| coin | こいん | アイテム（導入後） |

### 制御語

- もし / なら / あったら: 条件表現を記述する丁寧な書式。
- と: 複数条件の結合（OR）を表す。
- かい: 発火回数・繰り返し回数の指定。
- くりかえす / おわり: 複数行の反復ブロック。
- 追加の曖昧語は辞書に登録する際に構文テストを必須とする。

辞書は「語彙文字列 →意味ID」の役割とし、意味解析に単純な部分文字列一致だけを用いない。

## 3. 条件付き継続監視ルール

以下は同一のルールASTを生成することを目指す。

~~~text
もし まえに かべが あったら
とぶ
おわり
~~~

~~~text
かべならとぶ
かべとぶ
~~~

正規化後の概念AST:

~~~json
{
  "kind": "rule",
  "conditions": ["wall"],
  "operator": "or",
  "action": "jump",
  "maxFires": null
}
~~~

- `かべとぶ` は最初の壁だけではなく、そのプログラム実行中に登場するすべての壁を監視する。
- 各障害物IDについて、各ルールは受理成功を1回だけ記録する。フレーム継続での連射を防ぐ。
- アクションが実行可能でない場合は回数を消費しない。検知可能な間の再試行と期限切れの挙動はエンジン側で定義する。
- 条件付きルールはプログラム開始から有効であり、別の命令が動いている間も監視する（ハイブリッド方式）。

## 4. 複合条件

~~~text
かべとあなとぶ
~~~

は wall または hole を検知した際に jump する1つのルールとする（ANDではない）。

~~~json
{
  "kind": "rule",
  "conditions": ["wall", "hole"],
  "operator": "or",
  "action": "jump",
  "maxFires": null
}
~~~

- 結合対象が複数の場合は任意個数に拡張可能。
- 語の `と` は接続詞であると同時に動作語 `とぶ` の先頭である。最長一致・文法に基づく区切りを行い、部分一致だけに頼らない。
- 重複条件（例: 壁を2回）をどう扱うかは重複排除を既定とする案。
- 1つの対象が複数条件に一致しても、同じルールによる同一対象への発火は1回とする。
- 複合条件は「対象集合」を拡げる。異なる対象が同時に現れれば、それぞれ評価する。

## 5. 省略表現と一般化

| 入力例 | 正規化後の意味 | 注意 |
| --- | --- | --- |
| `まえにあながあったらとぶ` | hole → jump | 丁寧な記述 |
| `あなとぶ` | hole → jump | 短縮形 |
| `かべとあなとぶ` | wall OR hole → jump | 条件結合 |
| `まえとぶ` | ahead → jump | 汎用条件。障害物ごとの適否はゲーム側で判断 |
| `とぶ` | 1回の無条件ジャンプ | 継続監視ルールとは異なる |

短く書くほど必ず良いわけではない。`まえとぶ` が便利なステージも、敵が交じるため不適切なステージも用意する。

同義語は同じ動作・条件を意味するが、文字数スコアは実際に入力した文字数で比較する。

## 6. 発火回数制限

~~~text
かべ3かいとぶ
かべとあな3かいとぶ
~~~

後者は壁・穴の合計で最初の3回だけ、受理に成功したアクションを発火し、その後無効化する。

~~~json
{
  "kind": "rule",
  "conditions": ["wall", "hole"],
  "operator": "or",
  "action": "jump",
  "maxFires": 3
}
~~~

- 上限なしは `maxFires: null` で表す。
- 回数は「条件成立フレーム数」ではなく「アクションが受理された発火数」。
- 同じ障害物で成功済みの場合、それ以上の回数を消費しない。
- 同一tickで複数の対象が見えても、受理された動作と消費回数を決定論的に処理する。
- 回数0、極端に大きい回数、負値は拒否または明示した制限内に正規化する。ユーザーに静かな無限展開を起こさせない。

## 7. 無条件命令と手続き

~~~text
とぶ
3かいとぶ
はしる
~~~

- `とぶ` は無条件アクション1回で、永続監視ではない。
- `3かいとぶ` はジャンプを3回実行する逐次命令。
- `はしる` は移動モード変更の例。別の速度命令が来るまで有効にする案。
- 無条件ジャンプのクールダウン・着地待ち、および実行可能になるまでの待ちの上限は試験で決める。
- 先頭から順番に進む部分と、常時監視するルール部分を内部で分離する。
- 同じ入力を繰り返したときに、必ず同じ結果になることが必要。

## 8. 複数行のくりかえし

~~~text
3かいくりかえす
かべとぶ
おばけしゃがむ
おわり
~~~

インデントに依存せず、終端 `おわり` を用いる。

学習者の負担を下げるため、条件付きルールを繰り返し内に書いた場合は「対応するイベントを最大3回処理したら終了」する意味を基本案とする。条件なしの手続きは3回順番に実行する。

複数ルールが混じるブロックの「3回」を共通イベント列に対して数えるか、各ルール別に数えるかは未確定。後方互換性に影響するので、v1公開前にサンプルと自動テストで決定する。暫定実装では曖昧な組み合わせを明確な構文エラーにし、誤解を生む黙認を避ける。

## 9. 衝突するルール・同時発火

例:

~~~text
かべとぶ
おばけしゃがむ
~~~

同一tickに壁とおばけを検知したら、jump と crouch は併用可能で「しゃがみジャンプ」になる。衝突しないアクションは同時に処理する。walk と run のような同じプロパティを変更する命令は決定論的な優先順位を持たせる（最後の命令を優先する案）。

次の挙動は要試験:
- 同じ対象に対して `まえとぶ` と `かべとぶ` が同時発火した場合の重複抑制。
- 先にジャンプして空中にいる間に別の対象を検知した場合。
- しゃがみの持続時間と再発火時の延長。
- 速度変更とジャンプの同時処理順。

## 10. Parserパイプライン

1. 入力正規化: Unicode、空白、数字。
2. 字句解析: 辞書を利用したトークンの抽出。候補に複数の分割がある場合は文法で判定。
3. 構文解析: 条件、結合、アクション、回数、ブロックをASTに。
4. 意味検査: 未定義語、対応できない組み合わせ、使用不可の命令、上限超過。
5. 診断: 行・列、エラー種別、短い修正メッセージ。
6. 正規化されたASTをエディタとゲームエンジンで共用。
7. Interpreter: 継続監視ルールと逐次命令の実行位置を管理。

### 実装モデルの例

~~~ts
type Condition = "wall" | "hole" | "enemy" | "ahead" | "coin";
type Action = "jump" | "crouch" | "walk" | "run" | "wait" | "collect";

type Statement =
  | { kind: "rule"; conditions: Condition[]; operator: "or"; action: Action; maxFires: number | null }
  | { kind: "action"; action: Action; repeat: number }
  | { kind: "repeat"; repeat: number; body: Statement[] };
~~~

これは設計用の最小モデルであり、実際のASTはソース位置・トークン情報・診断情報・バージョンを保持する。

## 11. パーサー受け入れテスト

| 入力 | 期待 |
| --- | --- |
| `かべとぶ` | wall→jump、回数無制限 |
| `かべとあなとぶ` | wall OR hole→jump |
| `かべ3かいとぶ` | wall→jump、上限3 |
| `かべとあな3かいとぶ` | wall OR hole→jump、上限3 |
| `まえとぶ` | ahead→jump |
| `とぶ` | 無条件jump1回 |
| `3かいとぶ` | 無条件jump3回 |
| `3かいくりかえす ... おわり` | 構造を持つ反復として解析 |
| ブロックの `おわり` 不足 | エラー位置と具体的な説明 |
| 未知語 | 不明な語を特定、勝手に無視して成功扱いしない |
| ひらがな以外・異常に長い行 | フリーズせず分かりやすく拒否 |

構文テストには同義語、複合条件、繰り返し、曖昧な `と` の分割、空白の有無を必ず含める。
