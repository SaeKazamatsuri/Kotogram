# 2026年 ステージ・ゲームバランス改善 — 実装仕様（#9 / #10）

## 改善の対象と維持条件

公開中の7ステージ、固定60Hz、`GAME.runMultiplier=1.3`、ランキングの`stageVersion=2025-10-26`をベースラインとする。現行の公式結果/ランキングを破壊する変更はしない。

第1目標は「入門から応用への難易度の曲線を整える」。第2目標は「安全な低速/リスクを伴う高速/短いコードを別々の選択肢にする」。新しい命令・物理エンジン・ステージを先に増やすことは目的にしない。

## B1: 無変更の設計・探索

- `npm run validate:stages` と `npm run explore:stages` を使い、初心者/短縮/最速/最良総合（elapsedTicks×characters）の4指標を整理。既知最良値と探索上限を併記し、理論最適と呼ばない。
- `まえとぶ`の成功と失敗をそれぞれ誘発する仮説ケースを検討する。自動探索で失敗原因まで確認し、判定前に本番ステージに組み込まない。
- 走行だけで安全になる理由が`approachBase=72`、`reactionFrames=14`、`runMultiplier=1.3`、障害物間隔のどれに依存するかを仮説として分ける。ゲームコアを書き換えない。

## B2: ステージ3の構造改善案（公開は保留）

- 現行13障害物/1434tickから、学習目的を「壁・穴の複合条件＋おばけのしゃがみ」に絞る短縮版を開発用の別JSONで試作。例として障害物5〜8個程度を候補にするが、達成値ではない。
- ゴールまでの時間の改善は比較によって決める。目標値の仮説は初心者800〜1000tick程度であり、現在の実測値/実装済み数値とは扱わない。
- 現在の入門→複合条件→おばけ→回数制限という学習順序は維持する。説明文を増やすのではなく、障害物数/順序/初期位置で難度を調整する。
- 基準の`stage-3`は触らず、`experiments/`や検証用fixtureで成功/失敗/時間・文字数の差を確認する。

## B3: 速度の選択に意味を作る案

- 走行で早く障害物へ接近して危険になる区間と、歩行で反応余裕ができる区間を含む試作ステージを用意する。`はしる`＋適切な監視が常に正解になる設計を避ける。
- ただし高速操作の成否を1〜2tickの偶然のタイミングに依存させない。反応余裕は複数のGame Core tickで確保し、子どもがルールを理解して避けられることを優先。
- 物理パラメータの変更前に配置と`はしる/あるく`の組合せを試す。変更が必要な場合はエンジン版と基準スコアへの影響を別途検討。
- 初心者解法は引き続き安定してクリアできること。短いコードと速いコードの利害が少なくとも一部のステージで分かれ、総合順位で異なる解が競えることを目指す。

## バージョニング・公開の安全条件

- 公開ステージ配置・ゴール・障害物・クリア要件を変えるときは`manifest.version`と`app/scoring/score.ts`の各ステージ参照値、ランキングスコープ、サーバーの再実行検証をセットで見直す。
- 現行APIは`stageId+stageVersion+engineVersion+languageVersion+scoringVersion+seasonId`をスコープとしている。既存記録と新しいステージの記録を混ぜない。
- `getScoreReference`は各ステージにつき現在1バージョンの定義。改訂版を公開する場合、既存記録をどう閲覧・保持するかを決めてからスコア参照の設計を改める。
- `stage-checks`で基準解法・失敗解法を登録し、tickスナップショットとサーバー再検証を一致させる。既存本番のJSONを同名のまま黙って差し替えない。
- 公開変更の前にPlaywright E2E・全公開ステージ自動検証・Nodeの100回決定論テスト・公式記録の分離を確認する。

## B4: ステージJSONの整備（#4に依存）

- ステージ1〜3はJSON上の明示`id`・`learningObjectives`・障害物`id`が欠けている。今後のID移行では既存Game Coreの`wall:0`など自動生成された識別子との対応を検証。
- 現行Game Coreは壁・おばけ・穴の`objects[].id`をシミュレーション内の識別子に転写していない。表示/ゲーム内IDが部分的に違うことを前提に、移行前に状態や発火履歴の互換性をテストする。
- データ構造整備とステージ難度改変を同じPRで行わない。キャッシュ/ランキングに関わる版指定の変更を軽視しない。

## B2/B3の実験fixture（2026-10-20）

- `experiments/stages/stage-3-short.json`: ステージ3を障害物7件/goal3400に短縮、条件ORとおばけのしゃがみの学習を維持。
- `experiments/stages/speed-risk.json`: おばけと穴が近接し、無条件に前方を跳ぶ戦略と速度選択を比較する最小配置。
- 公開ステージには無い`jumpSensorProfile: centered-holes`を実験fixtureのみに指定可能にした。幅可変穴のセンサー開始距離を、壁との半幅差だけ補正し、最高点と穴の中央を揃える。公開JSONでは指定しないため、既存タイムとランキング版は不変。
- 実験fixtureはマニフェストに追加しない。最終公開はステージ版/engineVersionと再検証・採点基準の更新を独立した公開PRで行う。
