# 2026 実装ロードマップ・バックログ

## 1. 開発優先度

- P0: 学園祭の最低完成ライン。これが揃えば新機能を止めても運用できる。
- P1: 今年実現したい中核的拡張。
- P2: 時間が余れば導入する発展的体験。

優先順位は、依存する共通基盤→コア仕様→検証→UI→コンテンツの順。ビジュアルを先に完成させても、物理・ランキングの変更で作り直さないようにする。

## 2. Phase 0 — 仕様凍結と現行プロトタイプの棚卸し

### 作業

- [ ] 2025年の既存3ステージと現行解法を一覧化。
- [ ] 言語の正式文法・曖昧なケース・ブロック繰り返しの挙動を最終決定。
- [ ] ゲーム開始とゴールの公式tick境界を決定。
- [ ] アクション併用 / 排他と発火回数の更新タイミングを決定。
- [ ] 文字数の正規化ルール・最小文字数の定義を固定。
- [ ] ステージバージョンとランキングバージョンの命名規則を決定。
- [ ] 学園祭用の端末・画面幅・目標体験時間を確認。
- [ ] 基準解法と既知の最短・最速・最良総合を測るデータを用意。

### 完了条件

主要な命令に具体的な入力例と期待結果がある。未決定事項のうちEngine / Parserの実装を阻むものがゼロになっている。

## 3. Phase 1 — 基盤の分離と決定論化（P0）

### 作業

- [ ] Nuxt / TypeScriptのディレクトリを言語・ゲーム・描画へ分離。
- [ ] StageDefinitionとObject型・IDを共通化。
- [ ] 固定tickループ、状態遷移、再実行初期化を実装。
- [ ] 物理 / センサー / 衝突判定をGameCanvasから切り出す。
- [ ] 同時ジャンプ+しゃがみを回帰させる。
- [ ] 速度変更と検知範囲をパラメータ化。
- [ ] 描画なしでゲームが最後まで動くテストランナーを実装。
- [ ] 型検査・Lint・Vitestを追加。
- [ ] 既存ステージのクリア・失敗回帰テストを用意。

### 完了条件

描画を一切使わずにステージを実行でき、画面FPSが変わっても公式結果は同一。

## 4. Phase 2 — 言語刷新（P0）

### 作業

- [ ] ひらがな正規化、数字、Unicode、空白処理を実装。
- [ ] Lexer / Parser / AST / 診断を共通モジュール化。
- [ ] 辞書同義語・短縮表現を受け入れる。
- [ ] `かべとぶ` を継続監視する。
- [ ] `かべとあなとぶ` をOR条件として解析・実行。
- [ ] 条件付き回数制限と無条件繰り返しを実装。
- [ ] `くりかえす ... おわり` の確定済み範囲を実装。
- [ ] 複数ルールの同時発火・重複抑制・回数消費を実装。
- [ ] エディタの正誤判定をParserから取得。
- [ ] 無限展開 / 過長入力の防止。
- [ ] 言語の境界ケースをユニットテスト。

### 完了条件

同義表現が同じ意味を持ち、短縮構文・複合条件・発火制限がステージで動作する。

## 5. Phase 3 — ステージ自動検証とゲームバランス（P0〜P1）

### 作業

- [ ] ステージJSON検証の導入。
- [ ] 基準解法・短縮解法・高速解法・失敗解法の登録形式を決定。
- [ ] ステージごとの自動クリア / 失敗検証。
- [ ] 公式tick、文字数、総合積の出力。
- [ ] 同一結果の繰り返し検証。
- [ ] 初期の走行倍率・ジャンプ・しゃがみ・検知距離を調整。
- [ ] ステージの教育目的とレベルデザインチェックリストを整備。
- [ ] P1で限定的な自動解法探索を追加。
- [ ] 追加ステージを段階的に投入。

### 完了条件

全公開ステージのクリア可能性を自動検証でき、少なくとも一部に短縮・高速化の別解がある。

## 6. Phase 4 — 記録・採点・クラウドランキング（P0〜P1）

### 作業

- [ ] T_ref、C_ref、P_refと1000点超過のスコア計算。
- [ ] タイム / 文字数 / 総合の独立ベスト記録。
- [ ] SQLite-backed Durable ObjectsとWorkers APIの構成を確定。
- [ ] RankingDOのテーブル・インデックスと集計。
- [ ] ゲスト番号連番CounterDOの導入。
- [ ] 表示名入力、未入力時のゲスト番号、同名の許容。
- [ ] runId冪等性、最低限の入力値チェック。
- [ ] 3タブのランキング表示とスコア画面。
- [ ] ブラウザ内の自己ベスト保存 / 削除。
- [ ] クラウド保存失敗・オフライン時の簡単な再送導線。
- [ ] バージョン混在回避と環境分離。

### 完了条件

同時利用を想定したテストで登録・順位表示ができ、1000点超えを正しく表示。回線不調でもプレイ可能。

## 7. Phase 5 — 小学生向けUIとグラフィック（P0〜P1）

### 作業

- [ ] プレイ / 入力 / 結果 / ランキングの画面導線を改善。
- [ ] ソフトキーボードの五十音・濁音・小書き・数字・編集操作。
- [ ] IMEと物理入力の共存。
- [ ] 初心者向けヒントと構文エラー説明。
- [ ] キャラクター刷新とジャンプ / しゃがみアニメーション。
- [ ] ギミックの視認性・背景・効果音等を段階的に強化。
- [ ] スタッフ用の「つぎのひと」初期化。
- [ ] 固定文字サイズ前提での画面崩れ検証。

### 完了条件

マウスだけで命令を入力・修正・クリアでき、次の体験者へ確実に切り替えられる。

## 8. Phase 6 — 本番運用リハーサル

### 作業

- [ ] 本番同等Workers / DOへのデプロイ。
- [ ] ゲスト番号 / 3ランキングの同時登録を試験。
- [ ] 低FPS・長時間・非表示復帰・回線切断テスト。
- [ ] スタッフ手順書・障害時の復旧手順を確定。
- [ ] 全ステージの自動検証 / UI E2Eの結果を確認。
- [ ] スコア基準・ステージ・エンジン仕様バージョンを凍結。
- [ ] 必要に応じた切り戻し手順を用意。
- [ ] 学園祭会場で本番端末により通し運用試験。

### 完了条件

開催前に最低完成ラインの全受入項目が通り、当日のスタッフが迷わず操作・初期化できる。

## 9. 後回しにするP2

- 任意の複雑な自然言語やAIによる意味推測。
- 変数、入れ子、else、プレイヤー定義処理の高度化。
- ステージエディタと任意マップ作成。
- 他人のコード共有。
- アカウント、クロスデバイス連携、QR。
- 文字サイズ変更。
- 競技プラットフォーム級の不正監査。
- 大規模分析・複雑な運営ダッシュボード。

## 10. 主要依存関係

~~~mermaid
flowchart TD
    Spec[言語・時間仕様] --> Engine[決定論的Game Core]
    Spec --> Parser[Parser / Interpreter]
    Engine --> Validator[Stage Validator]
    Parser --> Validator
    Validator --> Baselines[基準解法・採点基準]
    Baselines --> Ranking[Ranking API / DO]
    Parser --> Editor[エディタ診断]
    Editor --> Keyboard[ソフトキーボード]
    Engine --> Renderer[ビジュアル強化]
    Ranking --> Rehearsal[学園祭リハーサル]
    Keyboard --> Rehearsal
    Renderer --> Rehearsal
~~~

## 11. 優先する「最小限の完成版」

P0安定版: 既存ステージ再現 + 同時アクション + 短縮構文 + 複合条件 + 回数限定 + 公式タイム + 3ランキング + ソフトキーボード + ステージ自動検証 + 共用端末リセット。

新ギミックや豪華な演出が未完成でも、このラインで本番運用できる状態を早めに確保する。
