# ゲームエンジン・実行モデル

## 1. 2025年版からの移行目的

現在の `GameCanvas.vue` はゲーム状態・物理・障害物検知・アクション実行・描画を同じコンポーネントに持つ。2026年は純粋なTypeScriptモジュールに分離し、Canvasは描画のみ担当させる。

目標: 描画のFPS、画面の表示有無、処理端末に左右されないクリア可否と公式ゲーム内タイム。

## 2. 役割分担

- GameState: プレイヤー位置、速度、姿勢、オブジェクト、アクション持続状態、クリア / 失敗、tick。
- StageDefinition: 障害物・ゴール・速度・クリア条件・使用可能命令。
- SensorSystem: 各障害物のID、種類、距離、検知の立ち上がり・有効範囲を通知。
- Interpreter: 条件付きルール、回数制限、逐次命令、発火履歴。
- ActionSystem: ジャンプ、しゃがむ、移動速度、同時実行の適用。
- PhysicsSystem: 位置・加速度・接地・穴落下、時間積分。
- CollisionSystem: 壁・おばけ・穴・コイン等の当たり判定。
- Renderer: GameStateをCanvasに描く。判定やタイムに影響しない。
- GameController: ready / running / paused / cleared / failed の遷移。

## 3. 更新順序（同じtickで毎回同じ）

初期案:

1. tick開始時点のWorldStateを取得。
2. SensorSystemで検知対象リストを生成。対象に安定したIDを付ける。
3. Interpreterで発火候補・逐次命令を評価。
4. ActionSystemで同時実行可能なアクションを合成し、排他的操作の競合を解決。
5. PhysicsSystemで1固定ステップ進行。
6. CollisionSystemで成否、アイテム、障害物通過を判定。
7. イベントを確定し、Interpreterの成功発火回数・対象処理済み集合を更新。
8. クリア / 失敗を判定し、tickを更新。
9. Rendererは最新のGameStateを読み込んで描画。

発火が受理されたかどうかの判定点と、衝突判定との順序は統合テストで固定する。後から変更する場合はエンジンバージョンを上げる。

## 4. 時計とシミュレーション

- 初期案: 60Hzの固定タイムステップ（1tick = 1/60ゲーム秒）。
- リアルタイム経過ではなく「実行済みの有効tick数」で公式タイムを出す。
- 実行前の編集時間、パース、通信、描画の待ち時間は記録に含めない。
- スタートからゴールまでの移動中だけ計測。UIの「やりなおす」を押したらtickを0に戻す。
- requestAnimationFrameは描画・進行要求に使えるが、物理の変数dtは固定。
- フレーム落ち・タブ復帰時のtick蓄積に上限を置き、一度に大量のtickを進めない設計。計測上の公平性を検証する。
- 検証ランナーでは描画なしでtickを進め、同じStateと結果を生成する。

## 5. プレイヤーとアクションの両立

ゲーム開始後、プレイヤーは手動操作しない。命令プログラムがすべての動作を決める。

| 同時動作 | 期待 |
| --- | --- |
| jump + crouch | しゃがみジャンプを許可 |
| jump + jump | 受理可能な1回のジャンプとして重複抑制 |
| crouch + crouch | しゃがみ継続 / 終了時間を適切に更新 |
| run + jump | 加速状態のジャンプを許可 |
| walk + run | 決定論的な優先順位（最後に有効化された速度変更を採用する案） |

しゃがみジャンプでは空中・地上とも当たり判定の高さが縮み、ジャンプ物理は保持する。既存挙動を回帰テストし、アニメーションと判定サイズに差が出ないようにする。

## 6. 条件監視・発火・回数制限

- 条件付きルールは実行開始からゴール・失敗まで監視。
- `かべとぶ` は検知したすべての壁ごとに処理機会を持つ。
- `かべとあなとぶ` はwall/hole集合のうち検知された対象に反応。
- 同じ対象IDに同じルールを何度も受理しない。連続tick検知でも発火数を重複加算しない。
- `かべ3かいとぶ` のようなルールは3回の動作受理後に無効化。
- 条件が成立しても動作が受理できない場合は回数を減らさない。
- 対象が有効検知範囲から離れた後の再登場・再発火は、同じ対象IDに対する重複防止を維持。
- アクションを受理したが障害物回避に失敗した場合でも、その発火自体は1回として記録する。

## 7. 速度のリスクとリターン

- 基準速度の歩行、高速移動の走行を用意する案。
- 初期バランス仮値: 走行は歩行の1.3倍。正式値は複数の動作検証・ステージ検証で確定。
- 速く動けばゴール時間を短縮できるが、障害物への反応可能な時間・距離や空中軌道が不利になりうる。
- 「とにかく走るだけ」で常に最良にならないよう、障害物間隔・ジャンプの持続・クールダウン・検知範囲を調整。
- キャラクター速度、ジャンプ初速、重力、当たり判定、センサー検知距離をパラメータ化する。
- バランス調整では「初心者解法」「高速解法」「短縮解法」のクリア成功率・タイムを比較する。
- ランダム性は基本的に避ける。必要な場合は固定シードとバージョンで再現できる形とする。

## 8. 障害物・センサー・コリジョン

- 各オブジェクトにstable ID、type、位置・大きさ・状態を設定。
- 検知範囲は絶対距離だけでなく速度・アクションの反応時間との関係を検証。
- 高速移動時のすり抜けを防ぐため、必要なら掃引判定（swept collision）を導入。
- 穴の「足先だけかかる」境界、壁の接触フレーム、空中おばけのしゃがみ判定をテスト。
- オブジェクトの画面外削除は描画最適化に留め、判定から早期に消失しないようにする。
- コインやスイッチはStageObjectの拡張ギミックとして段階的に実装。

## 9. 状態遷移

~~~mermaid
flowchart TD
    Ready[編集 / Ready] -->|実行| Running[Running]
    Running -->|衝突| Failed[Failed]
    Running -->|ゴール| Cleared[Cleared]
    Running -->|停止| Ready
    Failed -->|やりなおす| Ready
    Cleared -->|再挑戦| Ready
~~~

- 同時にclear/failを二重発火させない。
- running中にステージやプログラムが変更された場合は、リセットして明示的に再実行する。
- 再実行時にプレイヤー・障害物・ルール発火履歴・tickをすべて初期化する。
- エンジンが終了したら描画ループ・タイマーを確実に止める。

## 10. テスト可能なエンジンAPI（設計例）

~~~ts
type GameConfig = {
  tickRate: number;
  physicsVersion: string;
};

type SimulationResult = {
  outcome: "clear" | "fail" | "timeout";
  elapsedTicks: number;
  failureReason?: string;
};

function createGame(stage: unknown, program: unknown, config: GameConfig): unknown;
function stepGame(state: unknown): unknown;
function runToCompletion(state: unknown, maxTicks: number): SimulationResult;
~~~

これらは公開APIの確定形ではない。内部のEngineとStageDataの型を決定した後に具体化する。

## 11. 完了条件

- 描画なしで`runToCompletion`相当を実行できる。
- 2025年の既存ステージに対して基準解法が成立する。
- 60/120/144Hz想定の描画頻度を変えても公式tick数が同じ。
- しゃがみジャンプが機能する。
- 複合条件・回数制限が誤連射しない。
- 一時的な低FPS・非表示・ネットワーク不調で記録が破綻しない。
- 実行上限に達したプログラムが停止し、分かる理由を返す。
