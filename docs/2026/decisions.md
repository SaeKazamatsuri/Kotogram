# 設計決定記録と未決事項

更新: 2026-10-18。ここに記した確定事項はユーザーとの議論によるもの。技術実装の数値・手段は提案または検証待ちとして分離する。

## A. 確定した製品方針

| ID | 決定 | 理由 |
| --- | --- | --- |
| D-01 | ひらがなによる自由テキスト入力 | 小学生が自分で命令を書く学習 |
| D-02 | Tab / インデントによるスコープは使わない | 入力負担を下げる |
| D-03 | Scratch型のブロック / 事前命令パーツは使わない | 製品差別化 |
| D-04 | Parserは丁寧な構文、短縮形、同義語を許容 | コードゴルフ体験 |
| D-05 | `かべとぶ` はすべての壁へ継続反応 | 学習負担と文字数の低減 |
| D-06 | `かべとあなとぶ` のような複合条件を許可（OR） | 条件一般化 |
| D-07 | ハイブリッド型の言語実行モデル | 条件監視と逐次命令の両立 |
| D-08 | 明示回数制限のあるルールは指定回数の成功発火後に停止 | 分かりやすい回数指定 |
| D-09 | ジャンプとしゃがむは同時に実行可能 | 既存のしゃがみジャンプを保持 |
| D-10 | 速度と失敗リスクのトレードオフを設ける | タイムアタックを成立させる |
| D-11 | 公式タイムはキャラクターの開始からゴールまで | 入力速度・操作速度は競わない |
| D-12 | ステージ別にタイム / 文字数 / 総合ランキング | 3種類の改善目標 |
| D-13 | 高得点優位・基準1000点・1000超えも可能 | 直感的な競技評価 |
| D-14 | 名前空欄は「ゲストN」連番、入力時は入力名 | 登録の簡略化 |
| D-15 | 物理キーボードが苦手な人向けソフトキーボードを導入 | アクセスしやすい入力 |
| D-16 | ステージを自動検証できるようにする | レベルデザインの品質 |
| D-17 | QRによる体験結果の引き継ぎは廃止 | 開発費に見合わず、自宅の再スタートが容易 |
| D-18 | 文字サイズ変更は対象外 | 表示ズレの修正コストを回避 |
| D-19 | 小学生のイベント用途に過剰な認証・不正対策をしない | 開発費の優先度 |
| D-20 | ビジュアル強化、構文 / ギミック / ステージ追加は段階的に実施 | 安定性を優先 |

## B. 推奨設計・仮決め（承認済みの確定値ではない）

| ID | 仮案 | 確定の条件 |
| --- | --- | --- |
| P-01 | 60Hz固定tick | 端末・表示FPS比較テスト |
| P-02 | 走行速度は歩行の1.3倍から調整 | 複数ステージ / 解法の反復検証 |
| P-03 | Renderer、Physics、InterpreterをTypeScriptで分離 | 既存ステージ移行の検証 |
| P-04 | `くりかえす ... おわり` を複数行スコープとして扱う | 反復ルールを明確に仕様化 |
| P-05 | 回数は「アクションの受理成功」で消費 | 発火タイミングの具体テスト |
| P-06 | Workers API + SQLite-backed Durable Objects | デプロイ方式・規模 / コスト確認 |
| P-07 | StageごとのRankingDO + ゲスト採番CounterDO | トランザクション / ゲスト番号運用確認 |
| P-08 | 1000 × 基準値 / 結果のスコア式 | 画面の理解度・ランキング検証 |
| P-09 | 同端末の再挑戦はローカル識別子でベスト更新 | 共用端末初期化の運用 |
| P-10 | 既知の最良解を基準値に固定し、1000点超えを許容 | ステージ公開時の基準運用 |
| P-11 | CIにVitest / ステージ検証、Playwrightを導入 | コスト・実行速度確認 |

## C. 未決事項（実装前に解消する順序）

### ブロッカー

1. ブロック内に複数の継続監視ルールがあるとき、反復回数をルール別に数えるか、一連のイベント列として数えるか。
2. 複数ルールが同一対象に異なる動作を要求する場合の重複排除・優先順位。
3. 無条件命令（とぶ / まつ / はしる）の実行終了・待機判定と手続き位置の進み方。
4. ジャンプ不能のまま検知時間が過ぎた場合の「未使用回数」の挙動。
5. タイムのスタート / ゴールtick境界。
6. 文字数計算の空白・合成文字・無効文字ルール。

### ステージ公開前

7. 走行倍率・重力・ジャンプ初速・センサー距離・クールダウン。
8. ステージ・言語・スコアリングのバージョン命名と公開中の変更規則。
9. 2026年の公開ステージ数、学年別難易度とクリア条件。
10. 最短解法の探索制限と基準値の算出 / 凍結。
11. ランキング同点の表示仕様、上位表示件数。

### 運営前

12. ゲスト連番を学園祭単位・シーズン単位のどちらで発行するか。
13. 同端末の記録保持期間、ゲーム結果のクラウド保存期間と削除手順。
14. 本番の利用端末、想定同時アクセス数、最低画面幅。
15. 運営用初期化画面へのアクセス方法と本番フロー。
16. 同時登録のリトライ / 通信復帰時の最低限の扱い。

## D. 意図的に採用しないもの

- アカウント、ログイン、QR / 復帰コード、複数端末同期。
- ブロック式プログラミングUI。
- Tabやインデントの深さによる構文ブロック。
- 個人ごとの文字サイズ調整。
- 複雑な常時サーバー再計算アンチチート。
- 既知の最良解だけで理論最適性を断言すること。

## E. 変更管理

- 文書間で矛盾が生じた場合、明示的なユーザー決定（表A）が優先。表B・Cは設計提案とみなす。
- Parser、Engine、Stage、Scoreに影響する仕様変更は対象のバージョンを更新し、ステージ自動検証を再実行する。
- ランキング運用中の採点基準変更は旧ランキングを保存し、新ランキングバージョンに切り替える。
- バランス調整の結果は、変更前後の解法・クリア可否・tick数・文字数を残す。
